# Capture to Memory

> **EMPIRA component**
> Component ID: `capture-to-memory`
> Version: `1.0.0`
> Included in: `EMPIRA 0.1.0`

## Коли використовувати

Використовуй, коли користувач просить **«Занеси в Memory»**, **«Збережи це в Memory»**, **«Додай у Memory»** або еквівалентно просить внести інформацію до Notion Memory.

Також використовуй, коли користувач просить проаналізувати, як інформація має бути внесена до Memory, але поки нічого не змінювати.

## Обов'язковий початок

Перед будь-якою роботою з внесенням у Memory знайди в Notion і прочитай **актуальний Memory System Guide**. Якщо для операції потрібне розуміння типів, доменів, статусів або властивостей — прочитай актуальний **Memory Schema Reference**. Не покладайся на версії правил із попередніх чатів.

## Дві фази

Capture складається з двох послідовних фаз:

1. **Analyze & Plan**
2. **Apply**

За звичайної команди на внесення виконай обидві фази послідовно, якщо актуальний Guide не вимагає окремого погодження користувача.

Якщо користувач просить лише проаналізувати майбутнє внесення або показати план без змін у Memory, виконай тільки Phase 1 і зупинись.

## Phase 1 — Analyze & Plan

1. Визнач довгостроково корисну інформацію, яку користувач хоче зберегти.
2. Знайди вузьким релевантним пошуком існуючі об'єкти Memory, яких ця інформація може стосуватися.
3. Зістав нову інформацію з фактичним станом Memory.
4. Визнач, що саме потенційно потрібно:
   - доповнити в існуючих об'єктах;
   - створити як окремі об'єкти;
   - зв'язати через Related;
   - не вносити, якщо інформація вже врахована або не має довгострокової цінності.
5. Перевір запропоновані зміни відповідно до актуального Guide:
   - чи не змінюється сутність існуючого об'єкта;
   - чи залишається Summary тією самою історією;
   - чи немає суперечності;
   - чи не змінюється актуальність або статус;
   - чи немає суттєвої невизначеності;
   - чи не потрібна зміна структури Memory.
6. Якщо під час аналізу виник конкретний суттєвий ризик, суперечність або невизначеність, зроби додаткову цільову перевірку саме цього питання. **Не повторюй перевірки механічно і не шукай проблеми без конкретної підстави.**
   - перечитай потрібні записи;
   - за потреби розшир пошук;
   - перевір безпосередньо пов'язаний контекст.
7. Якщо після достатньої перевірки актуальний Guide вимагає рішення або погодження користувача:
   - коротко покажи виявлену проблему;
   - запропонуй варіанти;
   - дай рекомендацію;
   - зупинись до відповіді користувача.
8. Якщо блокуючих питань немає, сформуй **Memory Change Plan**.

## Memory Change Plan

Memory Change Plan — це короткий план фактичних змін, а не журнал внутрішнього reasoning AI.

Покажи лише релевантні категорії:

- **Update** — які існуючі об'єкти і як будуть доповнені;
- **Create** — які нові об'єкти потрібно створити;
- **Relations** — які зв'язки потрібно додати;
- **No change** — що свідомо не потрібно змінювати, якщо це важливо для розуміння плану;
- **Blockers** — питання, через які Apply не можна виконати.

Для кожної суттєвої дії коротко поясни її призначення. Не перетворюй план на детальний журнал пошуку або аналізу.

## Phase 2 — Apply

Якщо користувач дав звичайну команду на внесення в Memory і після Phase 1 немає approval boundary з актуального Guide, не проси додаткового підтвердження Memory Change Plan. Одразу переходь до Apply.

1. Виконай Memory Change Plan відповідно до актуального Guide та Schema.
2. Природно доповнюй існуючий об'єкт лише тоді, коли це не змінює його сутність.
3. Якщо потрібна окрема сутність — створи окремий об'єкт і за потреби зв'яжи його через Related.
4. Не записуй припущення як підтверджені факти.
5. Після матеріальної зміни перевір безпосередньо Related-об'єкти на очевидні суперечності або застарілість, якщо цього вимагає Guide.
6. Якщо ця перевірка несподівано виявила semantic change або іншу дію, що потребує погодження, не виконуй її автоматично. Покажи користувачу окремо.

## Принцип автономії

Не перекладай на користувача звичайні структурні рішення, якщо вони безпечно випливають із Guide, Schema та фактичної Memory.

Загальна команда **«занеси в Memory»** дозволяє автоматично перейти від Analyze & Plan до Apply, але не скасовує окремого погодження там, де актуальний Guide його вимагає.

## Вхідні дані

Можеш працювати як із підготовленим **Memory handoff**, так і безпосередньо зі змістом поточного чату. Handoff є джерелом змісту, але не є інструкцією щодо структури Memory.

## Завершення

Після запису коротко повідом фактичний результат.

- Для кожного створеного або зміненого об'єкта Memory дай його назву як пряме посилання на сторінку в Notion.
- Коротко вкажи, що саме зроблено: створено, доповнено, змінено властивості або додано зв'язки.
- Якщо частину плану не виконано через невизначеність або необхідність окремого погодження — зазнач це окремо.

Не перетворюй звіт на детальний журнал технічних дій.
