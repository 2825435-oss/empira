# Recall from Memory

> **EMPIRA component**
> Component ID: `recall-from-memory`
> Version: `1.0.0`
> Included in: `EMPIRA 0.1.0`

## Коли використовувати

Використовуй, коли користувач просить **знайти, згадати, показати, пояснити, зібрати або узагальнити** інформацію, що зберігається в Notion Memory.

Цей Skill призначений для **retrieval + synthesis + presentation**. Він не змінює Memory.

## Обов'язковий початок

Перед роботою знайди в Notion і прочитай актуальний `Memory System Guide`.

Якщо для правильної інтерпретації запиту потрібне розуміння типів, доменів, статусів, властивостей або меж об'єктів — прочитай актуальний `Memory Schema Reference`.

У межах однієї сесії не перечитуй ці документи без потреби, якщо вже прочитав актуальні версії.

## Retrieval workflow

1. **Визнач предмет запиту.** Зрозумій, який саме контекст потрібен користувачу. Не починай із читання всієї Memory.
2. **Знайди центральний об'єкт або невелику групу найрелевантніших об'єктів.** Використовуй вузький пошук.
3. **Прочитай знайдені об'єкти повністю**, якщо їхній вміст потрібен для відповіді.
4. **Розширюй контекст через `Related` лише за потреби.** Не читай усі пов'язані об'єкти механічно.
5. Для кожного пов'язаного об'єкта враховуй його **семантичну роль**. `Related` не означає, що всі об'єкти є частинами одного предмета. Пов'язаний об'єкт може бути, наприклад:
   - частиною самого предмета;
   - рішенням;
   - подією або історичним контекстом;
   - PoC / демо-кейсом;
   - джерелом або зовнішнім reference point;
   - завданням або відкритим хвостом;
   - іншим контекстом, корисним лише для конкретного запиту.
6. Якщо знайденого контексту недостатньо, зроби **наступний вузький крок пошуку**, а не глобальний пошук по всій Memory.
7. Зупини retrieval, коли зібраного контексту достатньо для повної відповіді на фактичний запит користувача.

## Синтез відповіді

Будуй відповідь **навколо питання користувача**, а не навколо структури бази.

Не використовуй один жорсткий шаблон для всіх тем. Структура відповіді має відповідати предмету запиту.

Коли це корисно, розділяй різні ролі інформації, наприклад:

- мета / суть;
- поточний стан;
- канонічні компоненти;
- прийняті рішення;
- перевірені результати;
- історичний контекст;
- PoC / приклади;
- зовнішні reference points;
- відкриті питання / наступні експерименти.

Не змішуй PoC, приклад або зовнішнє джерело з архітектурою лише тому, що вони пов'язані через `Related`.

## Точність

- Не вигадуй інформацію, якої немає в Memory.
- Не записуй і не подавай припущення як підтверджені факти.
- Якщо записи суперечать один одному або актуальність неясна — покажи це в відповіді замість самостійного переписування історії.
- Враховуй `Status`, змістовну `Date`, Summary та повний вміст сторінки, якщо вони важливі для визначення актуального стану.

## Provenance і посилання

Де це корисно для перевірки або подальшої роботи, додавай **прямі посилання або доступні цитати на конкретні Memory-об'єкти**, з яких походить суттєва інформація.

Пріоритет — не перевантажити відповідь посиланнями, а дати користувачу можливість швидко перейти до канонічного об'єкта або джерела.

Якщо платформа дозволяє нативні mentions / citations — використовуй їх. Якщо ні — дай звичайне пряме посилання на сторінку Notion.

## Межі Skill

- **Нічого не створюй і не змінюй у Memory**, якщо користувач окремо цього не попросив.
- Якщо під час Recall користувач просить внести знайдене або нову інформацію в Memory — передай дію workflow `Capture to Memory`.
- Не перетворюй Recall на повний аудит усієї Memory, якщо користувач прямо цього не просить.

## Орієнтир якості

Корисна відповідь повинна не просто перелічувати знайдені сторінки, а відновлювати для користувача **цілісний релевантний контекст**, зберігаючи межі між різними ролями об'єктів і можливість перейти до канонічних джерел.
