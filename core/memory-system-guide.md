# Memory System Guide

> **EMPIRA component**
> Component ID: `memory-system-guide`
> Version: `1.2.0`
> Included in: `EMPIRA 0.1.0`

## Призначення

Memory — спільна довгострокова пам'ять для користувача та AI-агентів.

Зберігай лише інформацію, яка має довгострокову цінність: допомагає зрозуміти контекст, актуальний стан, прийняті рішення або продовжити роботу в майбутньому. Не перетворюй Memory на архів чатів чи журнал усіх дій.

## Основні правила

1. **Спочатку шукай, потім записуй.** Перед створенням нового об'єкта перевір, чи вже існує відповідний. Шукай лише релевантний контекст і розширюй його через пов'язані об'єкти за потреби.
2. **Обирай між доповненням і новим об'єктом.** Пов'язану інформацію можна додавати до існуючого об'єкта, якщо це допомагає описати його контекст або розвиток. **Не змінюй сутність існуючого об'єкта, щоб умістити нову пов'язану інформацію.** Якщо для збереження нової інформації довелося б перетворити існуючий об'єкт на щось інше — створи окремий об'єкт і за потреби зв'яжи їх.
3. **Розрізняй доповнення і зміну змісту.** Порівняй `Summary` до і після потенційної зміни. Якщо він розповідає ту саму історію — це безпечне доповнення. Якщо історія змінюється — потрібне погодження користувача.
4. **Узгоджуй суперечності та зміни.** Якщо нова інформація суперечить існуючій, змінює її актуальність або статус — не змінюй запис автоматично. Покажи, що виявлено, запропонуй варіанти, дай свою рекомендацію та отримай погодження.
5. **Загальний дозвіл не замінює конкретного погодження.** Команди на кшталт «занеси основне в Memory», «збережи це» або «онови Memory» дозволяють працювати з Memory, але не є погодженням семантичної зміни чи іншої дії, для якої цей Guide вимагає окремого підтвердження. У таких випадках спочатку покажи конкретну запропоновану зміну та отримай явне погодження користувача.
6. **Зберігай корисну історію.** Якщо попереднє рішення було правильним свого часу, але його замінили — збережи його та зв'язок із новим. Якщо попередня інформація була помилковою — після погодження виправ її, не створюючи штучної історії помилки.
7. **Перевіряй пов'язані об'єкти.** Після суттєвої зміни перевір безпосередньо пов'язані записи на суперечності та застарілу інформацію. Семантичні зміни в них також потребують погодження.
8. **Не записуй припущення як факти.** Якщо інформація непідтверджена або неоднозначна — явно познач це або уточни перед записом.
9. **Не змінюй структуру Memory самостійно.** Якщо наявного типу, домену, властивості чи іншого елемента недостатньо, не підганяй інформацію під невідповідний варіант. Запропонуй необхідну зміну та отримай погодження.
10. **Використовуй актуальний `Memory Schema Reference`.** Він визначає поточні типи, властивості, домени, статуси та правила їх використання.

## Робота в межах сесії

`Memory System Guide` і потрібний для роботи `Memory Schema Reference` достатньо прочитати один раз на початку поточної сесії. Не перечитуй їх перед кожною операцією. Звернися повторно лише якщо потрібне уточнення або є підстава вважати, що документи змінилися.

## Короткі приклади

**Безпечне доповнення:** додався підтверджений технічний факт, але суть `Summary` не змінюється → доповнити без погодження.

**Зміна змісту:** нова інформація змінює попереднє рішення, тому `Summary` має розповідати іншу історію → запропонувати варіант зміни та отримати погодження.

**Новий об'єкт:** прийнято окреме рішення з власним довгостроковим значенням → створити новий об'єкт і пов'язати з відповідними існуючими.

**Принцип:** Memory повинна залишатися компактною, актуальною, несуперечливою та зрозумілою новому AI без читання історії попередніх чатів.
